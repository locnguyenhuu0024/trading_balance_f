# OptCodex-compatible CCB planning

1. Verify variant version and read its pinned `AGENTS.md` → `BASELINE_AGENTS_*.md`. If no variant is installed or lock drifts, STOP.
2. Confirm installed project domain by the single `ccb-domain-*.md` rule. For web load upstream frontend F0–F3; for mobile use platform-native domain rules and **do not** assume web tooling; for backend follow API/data/concurrency domain rules. `model-routing.json` is advisory; it does not authorize changing OptCodex E0–E5. Follow `PLANNING_RULES.md`: choose S/M/L and C/R/E classification by actual work, inspect only allowed non-protected context, resolve ambiguities before canonical SPEC/PLAN/TASK.
2a. For a long planning cycle, noisy context, or a compact/resume transition, load pinned `CONTEXT_DISCIPLINE_RULES.md` on demand. Keep a bounded TARGET/BOUNDARY/EVIDENCE/NEXT/OPEN frame; use targeted source and evidence over broad searches. Neither a summary nor repeated speculation changes approved requirements.
2b. Optional context discovery: for unfamiliar cross-module code flows, consult /ccb-graph-context against an existing local graph before preparing SPEC/PLAN; validate graph freshness and verify relevant source_file/source_location against permitted source. Skip for trivial E0 and when missing/stale. Never auto-install/rebuild Graphify, forward graph output to a different provider, or treat graph results as authoritative code/requirements.

3. Default advisor pass is **Claude Opus 5.5 Medium, in the same coordinator session** (user-selected; effective runtime model/effort cannot be programmatically enforced by CCB). Analyze permitted repository evidence, requirements, alternatives, assumptions, risks, boundary contracts, open questions and proposed independently auditable tasks before authoring canonical SPEC/PLAN/TASK. Do not run Codex planning transport or prepare Sol packets by default.
3a. Classify material planning workstreams. For two or more independently analyzable material workstreams, including material backend + frontend, the pinned OptCodex mandatory fan-out gate applies: dispatch **separate native Claude reasoning subagents** when the runtime supports child dispatch. Give each child a bounded workstream/evidence contract, request Opus 5.5 Medium where explicit child model selection exists, collect distinct terminal results via the native collect mechanism and record actual model/effort only if observable. Reconcile disagreements, API/data contracts and assumptions in the main Opus coordinator session. One session doing two analyses is NOT evidence of two separate reasoning children. If child dispatch is unavailable, record `Fan-out Required: YES`, `Fan-out Compliance: UNAVAILABLE` and `RUNTIME_CHILD_DISPATCH_UNAVAILABLE`; do not fabricate PASS.
3b. Only if the user explicitly requests an external Sol proposal, use `/ccb-sol-plan` after separately reviewed authorization to share a curated non-protected packet. Sol output is optional, non-canonical and never substitutes for mandatory fan-out evidence, user approval or independent audit. Failure or unavailability of this optional path must not block the default Opus planning workflow.
4. On frontend variants, apply `FRONTEND_DESIGN_RULES.md` and F0–F3. All variants apply `PONYTAIL_RULES.md` for minimal complete change. Personal variants preserve RTK/Headroom; company variants record QA impact.
5. For each newly finalized canonical TASK, record a task event once using `python3 scripts/ccb/task_ledger.py plan --project <planning-root> --plan-id <plan_id> --task-id <task_id> --domain <backend|web|mobile>`. This log must be durable outside Git. A retry/rework does not create a new task ID unless it is genuinely a distinct task contract. Record E0–E5 based on implementation entropy; defaults Terra/low E0, Terra/medium E1, Sol/low E2, Sol/medium E3, Sol/high E4, Sol/xhigh E5. Nondefault allowlisted alternatives require separate `route_override` approval; never silently escalate or reclassify legacy task IDs. Preserve exact model+effort binding and approval. Tasks must match OptCodex `TASK_TEMPLATE.md`: explicit Agent Role, E0–E5, Target Model, Target Effort, predecessors, Allowed Write Surfaces, RED/GREEN, Task Buildability Gate and verification ceiling.
6. Present plan and checklist, avoiding repeated lengthy rationale: state decision, evidence, tradeoff and open question once. Do not code. Wait for explicit approval of this version of the plan before dispatch; Git worktree operations require separate approval. If context needs compaction, preserve exact PLAN revision and approval provenance; `/compact` does not approve a plan.
7. After authorization, prepare `CCB_JOB_TEMPLATE.json`-shaped manifest with exact variant/version/revision, E-route binding and truthfully recorded planning fan-out.
